# Interview walkthrough

Start with the one-page strategy. A visitor must find a product, reach its correct detail page and understand empty results or a sign-in boundary. An integrator must receive usable identities and distinguish rejected requests from successful queries. These risks drove the seven browser scenarios and seven API cases. [Strategy](test-strategy.md) · [Coverage](test-coverage.md)

**Show the API boundary.** Open the fetch client, then API-TEST-02 and API-TEST-06. The client returns status and unknown JSON. TypeScript checks how our code handles those values. Runtime checks establish that the actual data has the fields we use. A collection/detail match needs two independent reads within one test. A changed name deserves investigation because live records can change between reads. Missing credentials yield HTTP 401 and OAuth error properties. An unknown field yields HTTP 200 and a GraphQL error identifying the field. Neither case should pass on a network failure.

**Explain isolation.** Every fetch builds headers for its requested auth mode. Omission and deliberate invalidity never consult the real token. Two sequential requests fit within the Bun test timeout. Pagination checks the opaque continuation and its boundary cursors. The fixed window reduces churn but still needs enough records. Browser contexts start fresh and discover current data within each scenario.

**Demo from the root.** With your private environment configured, run `bun test -t API-TEST-02`. Show `bun run test:e2e --list` and the E2E-02 source. On an accessible authorized runner, run `bun run test:e2e --grep E2E-02`. Explain the recorded 403 and separate historical API success, browser discovery, headed observations and actual scenario outcomes. A preflight failure blocks release evidence. The local workflow has yet to run on GitHub.

**Extend the suite.** For an API case, first inspect the documented query and confirm a bounded read. Add a uniquely named Bun test under `tests/api/specs`, choose its request-local auth mode, check status and envelope, and assert the relevant runtime fields. Run it alone with `bun test -t <ID>`. For an E2E case, confirm the user journey and locators in a fresh accessible context. Add a Playwright test under `tests/e2e/specs`, discover its own data, perform the public interaction and assert the user-visible outcome. List it, run by ID, then run it alongside the existing suite. Keep helpers local until behavior repeats.

**Release and operations.** Gate changes on static checks and relevant API and browser jobs. Inspect HTTP status, GraphQL errors and access diagnostics separately. In production, monitor discovery availability, detail destination errors, API latency and authentication rejection rates. Investigate spikes against a baseline, separate access challenges from application regressions and use controlled release checks before escalating. Rehearse adding a case yourself before the interview.
