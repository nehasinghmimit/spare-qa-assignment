# Product Hunt: test strategy

**Objective and priorities.** As sole QA, I would protect visitors' ability to discover relevant products, reach the correct details, and trust the information presented. Broken discovery costs makers visibility; mismatched identities or misleading API responses undermine user and integrator trust. Within the assignment's 4–6 hours, prioritize these risks and authentication boundaries over cosmetic completeness.

**Evidence and uncertainty.** Read-only reconnaissance on 31 October 2026 retrieved the [homepage](https://www.producthunt.com), categories and a linked product detail page through web retrieval; search and sign-in controls, and a “Login to comment” prompt, were present. Local headless Chromium returned HTTP 403, “Just a moment…”. Interactive search, navigation and authorization enforcement remain unverified. Official [API documentation](https://api.producthunt.com/v2/docs) requires a token and describes public scopes; the linked schema documents post queries and paginated connections. No authenticated API requests were made. Search reliability and consistent UI/API identity mapping remain assumptions to investigate.

**Scope and approach.** Phase 2 exploration will follow public listing-to-detail discovery, categories or available search, and logged-out action boundaries. Select 5–8 Playwright E2E scenarios around successful discovery, correct destinations and understandable empty/error states, conditional on observed behavior. Select 5–8 TypeScript/Bun API tests around public post retrieval, identity and field contracts, pagination, and meaningful authentication/query negatives. These are provisional coverage themes, not executed cases. API assertions must inspect HTTP behavior and the GraphQL data/errors envelope, including relevant runtime types; a successful HTTP status alone is insufficient. Record reproducible evidence and separate confirmed defects, observations and questions.

**Data and ethical limits.** Discover suitable public records within each test; compare stable identity rather than today's names, rankings or vote totals. Use independent setup and fresh browser contexts; avoid test-order dependencies and cross-run shared state. Keep requests sequential, bounded and read-only. Limit security checks to authorized access boundaries and error disclosure using public data or our own credentials. Exclude account creation, votes/comments, private third-party data, intrusive scanning, load testing, CAPTCHA bypass and third-party sign-in automation. Redact tokens and evidence before sharing.

**Execution and diagnosis.** Run suites independently with Bun, strict TypeScript and headless Chromium; use role/label locators and condition-based assertions. One browser worker and zero retries expose instability. Later CI will separate API and E2E jobs and protect secrets. Classify failures as product, test, credential or access/environment issues; inspect redacted traces/screenshots. Missing credentials must fail clearly; access challenges are limitations, never passing behavior.

**Completion and follow-up.** Completion requires evidence-linked priorities, 5–8 real tests per suite, repeatable headless execution, documented outcomes and unresolved risks, and reproducible setup. Blocked coverage stays incomplete; seek an authorized accessible environment before claiming E2E confidence. This phase completes strategy only. With production ownership, monitor discovery availability, detail-load errors, API latency/error rates and authentication failures; extend accessibility, mobile/cross-browser coverage and controlled-data testing next.
